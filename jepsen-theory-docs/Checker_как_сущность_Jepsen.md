# Checker как сущность Jepsen

## Назначение Checker в Jepsen

Checker — это компонент теста, реализующий протокол `jepsen.checker/Checker` с единственным
методом `check [checker test history opts]`. В отличие от Client и Nemesis, Checker не
участвует в тесте «в реальном времени»: он не порождает операций, не получает их от
Generator и не взаимодействует с тестируемой системой напрямую. Его задача — чисто
аналитическая пост-обработка: после того как тест закончился и вся история операций
(и клиентских, и nemesis) уже накоплена, checker анализирует эту историю целиком и
выносит вердикт, сохранила ли система заявленные гарантии.

Результат работы checker'а — мапа вида

```clojure
{:valid? true}
```

или

```clojure
{:valid?       false
 :some-details ...
 :failed-at    [...]}
```

`:valid?` может принимать одно из трёх значений, упорядоченных по «серьёзности»
(`jepsen.checker/valid-priorities`):

| `:valid?`  | Приоритет | Смысл |
|---|---|---|
| `true`     | 0   | Нарушений не найдено |
| `:unknown` | 0.5 | Проверить не удалось (например, не набралось данных) |
| `false`    | 1   | Найдено нарушение гарантии |

Это упорядочивание используется, когда несколько checker'ов объединяются через
`checker/compose` — итоговый `:valid?` всего теста берётся как самый «плохой» из
результатов всех under-checker'ов (`merge-valid`). Так же, как в Client три исхода
операции (`:ok`/`:fail`/`:info`) задают семантику отдельной операции, три значения
`:valid?` задают семантику результата всего теста.

Метод `check` принимает `opts` — мапу с настройками выполнения, например
`:subdirectory` — куда писать побочные файлы (графики, отчёты), если checker их
генерирует.

## Откуда checker получает history

History собирается на протяжении всего теста функцией `jepsen.core/run!` — каждая
операция, прошедшая через Client (и Nemesis), дописывается в общий лог по мере
выполнения теста. Checker получает эту историю только один раз, уже целиком, на
финальном шаге теста — в функции `analyze!`:

```clojure
(defn analyze!
  "After running the test and obtaining a history, we perform some
  post-processing on the history, run the checker, and write the test to disk
  again. Takes a test map. Returns a new test with results."
  [test]
  (info "Analyzing...")
  (let [test (assoc test :results (checker/check-safe
                                     (:checker test)
                                     test
                                     (:history test)))]
    (info "Analysis complete")
    (if (:name test)
      (store/save-2! test)
      test)))
```

То есть источник history для checker'а — поле `:history` итогового test-мапа,
сформированное к моменту завершения `run-case!` (после того как отработали все
клиенты, nemesis и время теста истекло). Сам checker вызывается не напрямую, а через
обёртку `check-safe`:

```clojure
(defn check-safe
  "Like check, but wraps exceptions up and returns them as a map like

      {:valid? :unknown
       :error {:via [{:type clojure.lang.Exceptioninfo, ...}] ...}"
  ([checker test history]
   (check-safe checker test history {}))
  ([checker test history opts]
   (try (check checker test history opts)
        (catch Exception t
          (warn t "Error while checking history:")
          {:valid? :unknown
           :error (datafy t)}))))
```

Здесь прослеживается та же двухуровневая логика обработки ошибок, что и в Client
(`with-conn` vs `try/catch` в `invoke!`): сам checker может упасть с исключением
(например, из-за бага или неожиданной формы данных), и `check-safe` — это внешний
слой, который перехватывает такое исключение и превращает его в семантически понятный
результат `{:valid? :unknown, :error ...}`, не давая тесту упасть целиком. Именно
поэтому Anthropic-Jepsen различает «не проверено» (`:unknown`, ошибка самого
checker'а) и «проверено, и найдено нарушение» (`false`).

После получения результата `log-results` выводит его в stdout и печатает один из трёх
вердиктов в зависимости от `:valid?`:

```clojure
(case (:valid? (:results test))
  false     "Analysis invalid! (ﾉಥ益ಥ）ﾉ ┻━┻"
  :unknown  "Errors occurred during analysis, but no anomalies found. ಠ~ಠ"
  true      "Everything looks good! ヽ(‘ー`)ノ")
```

## Структура history подробнее

История (`history`) — это не абстракция конкретно checker'а, а сквозной артефакт всего
теста: единственный объект, через который Generator, Client и Nemesis «общаются» с
checker'ом, ничего не зная о нём напрямую. Пока Generator выдаёт операции, а Client
(и Nemesis) их выполняют, `jepsen.core/run!` дописывает в `history` запись при каждом
значимом событии. К моменту вызова `analyze!` эта последовательность уже неизменна —
checker получает её как готовый, «замороженный» лог.

### Анатомия одной записи

Каждая запись — это Clojure-мапа. Минимальный необходимый набор полей:

| Поле | Значение |
|---|---|
| `:type` | `:invoke` (операция начата) / `:ok` / `:fail` / `:info` (операция завершена — три исхода, разобранные в документе про Client) |
| `:process` | Логический номер клиентского процесса (0, 1, 2, ...), либо `:nemesis` для операций nemesis |
| `:f` | Имя операции (`:add`, `:read`, `:kill`, `:start-halves` и т.п.) |
| `:value` | Полезная нагрузка: то, что передал Generator во `:invoke`, и то, что вернул Client/Nemesis в завершении |
| `:time` | Момент события в наносекундах, отсчитанный от начала теста (см. `util/with-relative-time` в `run!`) |
| `:index` | Порядковый номер записи в общей истории — присваивается монотонно по мере записи событий |

Пример пары `:invoke`/`:ok` для клиентской операции чтения (все поля явно, как они
реально выглядят в history):

```clojure
{:type :invoke, :process 0, :f :read, :value nil,  :time 1234500000, :index 40}
{:type :ok,     :process 0, :f :read, :value #{1}, :time 1234700000, :index 41}
```

### Правило парности invoke/completion

Каждый логический процесс (число в `:process`) в Jepsen строго последователен: он
выдаёт `:invoke`, ждёт своё завершение (`:ok`/`:fail`/`:info`) с тем же `:process` и
тем же `:f`, и только после этого может выдать следующий `:invoke`. Именно эта
дисциплина позволяет checker'ам (в первую очередь Knossos, см. ниже) вычислять
интервалы конкурентности операций: операция B пересекается по времени с операцией A,
если `:invoke` операции B появился в истории раньше, чем завершение операции A. Nemesis
(`:process :nemesis`) следует тем же правилам инвок/завершение, но, как правило, ведёт
собственную последовательность независимо от клиентских процессов (см. документ про
Nemesis — там nemesis-операции `:start`/`:stop` тоже фиксируются в общей history именно
для того, чтобы можно было потом сопоставить аномалии с конкретными отказами по
времени).

### Клиентские и nemesis-операции перемешаны в одной ленте

История одна на весь тест: в неё вперемешку, в порядке фактического возникновения,
попадают и операции клиентов (`:f :add`/`:read`), и операции nemesis
(`:f :start-halves`/`:kill`/`:switch` и т.п.). Например, реалистичный фрагмент истории
patroni-теста может выглядеть так:

```clojure
[{:type :invoke, :process 0,        :f :add,   :value 41, :index 118}
 {:type :invoke, :process :nemesis, :f :kill,  :value nil, :index 119}
 {:type :ok,     :process 0,        :f :add,   :value 41, :index 120}
 {:type :info,   :process :nemesis, :f :kill,  :value [:killed :postgres :on :n1], :index 121}
 {:type :invoke, :process 1,        :f :read,  :value nil, :index 122}
 {:type :ok,     :process 1,        :f :read,  :value #{41}, :index 123}]
```

Именно поэтому checker, которому нужны только клиентские данные (как `patroni-set`),
обязан явно отфильтровать nemesis-записи. `patroni-set` делает это неявно, через
`(r/filter #(= :add (:f %)))` / `(r/filter #(= :read (:f %)))` — операции nemesis
просто не проходят фильтр по `:f`, потому что у них другие значения этого поля.
Встроенные checker'ы (`jepsen.checker/stats`, `set` и т.д.) делают это явно и более
общим способом, через `(h/remove h/invoke?)` и `h/client-ops` — специальную функцию,
которая отбрасывает вообще все операции с `:process :nemesis`, независимо от того,
какое у них `:f`.

### Ручной подход (`patroni-set`) vs специализированное API `jepsen.history`

`patroni-set` обходит `history` напрямую как обычную Clojure-последовательность, через
`clojure.core.reducers` (`r/filter`, `r/map`, `into`) — три независимых прохода по
истории (для `attempts`, `adds`, `final-read`). Это просто и понятно, но не
масштабируется: каждый проход — это полное сканирование всей истории, без переиспользования
уже вычисленного, и без возможности быстро найти «где завершилась вот эта конкретная
операция».

Современный `jepsen.checker` (namespace `h`, т.е. `jepsen.history`) устроен куда
богаче — это не просто вектор мап, а специализированная структура данных с
предвычисленными индексами, которая даёт:

- **Предикаты по исходу**: `h/invoke?`, `h/ok?`, `h/fail?`, `h/info?`, `h/has-f?` —
  аналоги ручных `(= :type ...)`/`(= :f ...)` проверок из `patroni-set`, но
  как переиспользуемые функции.
- **Прыжки между invoke и завершением конкретной операции**: `(h/completion history
  op)` — по операции `:invoke` мгновенно найти её завершение (или узнать, что его нет),
  и наоборот `(h/invocation history op)` — по завершению найти исходный `:invoke`. Это
  используется, например, в checker'е `Counter`, где для операции `:add` нужно
  заранее знать, чем она закончится, чтобы решить, учитывать её в верхней границе или
  нет.
- **`h/client-ops`** — единая функция «выкинуть nemesis из истории», о которой сказано
  выше.
- **`h/task` и `h/tesser`** — построение дерева параллельных вычислений (fold) поверх
  Tesser вместо последовательных проходов reducers. Так, в checker'е `Set` (аналог
  `patroni-set`, но встроенный) `attempts`, `adds` и `final-read` считаются не тремя
  последовательными проходами, а тремя параллельными задачами
  (`h/task history attempts [] ...)`, которые можно исполнять на разных ядрах и с
  меньшим пиковым потреблением памяти на очень длинных историях (сотни тысяч операций
  — обычное дело при многочасовых прогонах).

Иными словами, `patroni-set` — это учебный, «руками» написанный вариант той же логики,
которую `jepsen.checker/set` реализует поверх куда более развитого внутреннего API для
работы с history; смысл вычислений при этом идентичен.

### `:index` как порядок «в ленте», а не гарантия wall-clock времени

Важный нюанс, напрямую влияющий на анализ `final-read` в `patroni-set` (см. ниже): в
подавляющем большинстве операции `:index` монотонно совпадает с реальным временем
записи события (`:time`), но полагаться стоит именно на `:index`/порядок в
последовательности, а не додумывать реальные часы — `:time` считается относительно
старта теста на управляющей ноде и не является распределённым таймстемпом всех узлов
кластера (для этого в тесте отдельно используется `clock-plot`/`jepsen.nemesis.time`,
описанные в документе про Nemesis).

## Общая инфраструктура checker'ов (контекст)

В `jepsen.checker` кроме протокола есть несколько служебных конструкций, которые стоит
иметь в виду, чтобы понимать место `patroni-set` в общей картине:

- **`compose`** — объединяет мапу `{имя checker}` в один checker, прогоняющий их все
  (возможно параллельно, `pmap`) и агрегирующий `:valid?` через `merge-valid`.
- **`concurrency-limit`** — ограничивает число одновременных выполнений тяжёлого
  checker'а семафором.
- **`unbridled-optimism`** и **`noop`** — тривиальные заглушки (`{:valid? true}` и
  `nil` соответственно) для тестов/отладки.
- Готовые built-in checker'ы для типовых структур данных: `set` / `set-full` (множества
  через add/read), `queue` / `total-queue` (очереди через enqueue/dequeue),
  `counter` (монотонный счётчик), `unique-ids` (генератор уникальных id),
  `linearizable` (полная линеаризуемость через Knossos), `stats`,
  `unhandled-exceptions`, графические (`latency-graph`, `rate-graph`, `clock-plot`,
  `op-color-plot`), `log-file-pattern` (grep по логам сервиса).

Важно: в `postgres-test` (postgres.clj) используется именно встроенный
`checker/compose` с набором стандартных checker'ов, включая `(:checker workload)` —
т.е. Postgres-тест полагается на общую инфраструктуру `jepsen.checker`. Patroni-тест,
напротив, **не использует ничего из этого набора для проверки корректности данных** —
он определяет свой собственный checker `patroni-set` вручную, через `reify
checker/Checker`, по образцу встроенного `checker/set`, но не идентично ему. Это прямая
аналогия с тем, как Patroni-тест не использует `jepsen.nemesis.combined`, а собирает
`nemesis/compose` вручную из-за нестандартных операций `:kill`/`:switch`.

## Knossos и Elle — специализированные checker'ы консистентности

`patroni-set` и встроенный `checker/set` — это самый простой, «грубый» класс
checker'ов: они сравнивают финальные множества и вообще не смотрят на порядок событий.
Для более строгих гарантий (линеаризуемость, изоляция транзакций) в экосистеме Jepsen
есть две отдельные библиотеки, каждая из которых сама реализует протокол
`knossos.op`/`jepsen.checker` и подключается как ещё один вариант checker'а —
[`jepsen-io/knossos`](https://github.com/jepsen-io/knossos) и
[`jepsen-io/elle`](https://github.com/jepsen-io/elle). Обе они используются в самом
`jepsen.checker`, что видно прямо в его require-секции: `[knossos [model :as model]
[op :as op] [competition :as competition] [linear :as linear] [wgl :as wgl] [history
:as history]]` и `[knossos.linear.report :as linear.report]`.

### Knossos — проверка линеаризуемости против модели

Knossos — отдельная библиотека («названа в честь руин, где нашли линейное письмо Б» —
отсюда каламбур «проверяем, линейна ли история»), которая проверяет, можно ли выстроить
все операции истории в единый последовательный (single-threaded) порядок, не
противоречащий их реальным интервалам времени и подчиняющийся заданной **модели**
(register, cas-register, mutex, множество и т.п.). В отличие от `patroni-set`, который
смотрит только на итоговое состояние, Knossos пытается найти *хоть один* допустимый
линейный порядок операций (или доказать, что такого порядка не существует), то есть
реально учитывает пересечения интервалов `:invoke`/`:ok`/`:fail`/`:info` конкурентных
операций — ту же самую семантику трёх исходов, что описана в документе про Client.

В `jepsen.checker` эта проверка подключена как отдельный checker `linearizable`,
который виден прямо в общем коде checker.clj:

```clojure
(defrecord Linearizable [algorithm model]
  Checker
  (check [this test history opts]
    (let [a ((case algorithm
               :linear       linear/analysis
               :wgl          wgl/analysis
               competition/analysis)
             model history)]
      (when-not (:valid? a)
        (linear.report/render-analysis! history a ... "linear.svg"))
      ...)))
```

Knossos поддерживает несколько алгоритмов поиска (можно указать `:algorithm`):

- **`:linear`** — алгоритм Гэвина Лоу (Lowe) — «just-in-time» graph search;
- **`:wgl`** — усовершенствование алгоритма Винга-Гонга (Wing & Gong), доработанное
  Lowe, Horn и Kroening (комбинация обоих подходов «наперегонки» дала на порядки
  большую скорость на историях Tendermint, по опыту самой команды Jepsen);
- по умолчанию используется `competition/analysis` — запускает несколько стратегий
  параллельно и берёт ту, что завершится первой.

Если история нелинеаризуема, Knossos не просто говорит «false» — он строит
`linear.svg` с наглядной визуализацией минимального противоречия (какая операция не
укладывается ни в один порядок и почему).

**Ограничение Knossos — производительность.** Поиск по всем допустимым перестановкам
операций растёт экспоненциально с ростом параллелизма (числа одновременно активных
процессов): по данным самой команды Jepsen/Elle, Knossos часто «упирается» уже на
нескольких сотнях операций, тогда как Elle (см. ниже) на тех же данных обрабатывает
сотни тысяч операций за секунды. Именно поэтому Knossos применяется точечно — там, где
модель простая и одноключевая (регистр, CAS-регистр, мьютекс, небольшая очередь), а не
для полноценных многотабличных SQL-транзакций.

### Elle — проверка транзакционной изоляции через поиск циклов

Elle — более новая (2020, Kyle Kingsbury и Peter Alvaro) библиотека для
чёрно-ящичной (black-box) проверки консистентности **транзакций**, а не отдельных
операций. Идея: по наблюдаемым клиентским чтениям/записям Elle строит граф зависимостей
в духе формализма Adya (рёбра write-write, write-read, read-write между
транзакциями) и ищет в этом графе циклы. Наличие цикла математически доказывает, что
такая история не могла быть порождена системой с заявленным уровнем изоляции — «как
хороший адвокат, Elle ищет последовательность событий в истории, которая физически не
могла произойти в этом порядке», и по этому противоречию строит доказательство
несостоятельности истории.

Elle умеет находить и классифицировать конкретные аномалии изоляции — G0 (грязная
запись), G1a/G1b/G1c (разные виды грязного чтения), G-single, G2-item, G2 (аномалии
сериализуемости) и т.д. — вплоть до определения, какому конкретному уровню изоляции
(read committed, repeatable read, snapshot isolation, serializable...) соответствует
или не соответствует наблюдаемая история.

Ключевые отличия от Knossos:

| | Knossos | Elle |
|---|---|---|
| Единица проверки | Отдельная операция над одной моделью (регистр, CAS и т.п.) | Транзакция (несколько операций сразу, чтения+записи по многим ключам) |
| Метод | Полный перебор допустимых линейных порядков | Построение графа зависимостей + поиск циклов |
| Сложность | Экспоненциальная по параллелизму | Практически линейная по длине истории, ~константная по параллелизму |
| Что проверяет | Строгую линеаризуемость относительно конкретной модели | Семейство уровней транзакционной изоляции (от read uncommitted до strict serializable) |
| Типичный масштаб | Сотни операций | Сотни тысяч транзакций |

В современных версиях `jepsen.checker` есть отдельные обёртки поверх Elle (например,
семейство «cycle»-тестов для списков-с-append, множеств регистров и т.п.), но в
предоставленном коде `checker.clj` прямого require Elle нет — там показан только слой
Knossos (`checker/linearizable`). Это означает, что в тестах Postgres/Patroni,
рассматриваемых в этих документах, транзакционная изоляция через Elle не проверяется
вовсе — оба теста ограничиваются либо `checker/set`-подобной проверкой (`patroni-set`),
либо обычными служебными checker'ами (`stats`, `perf`, `unhandled-exceptions`), не
затрагивающими ни линеаризуемость, ни изоляцию транзакций.

### Где на этой шкале находится `patroni-set`

Если выстроить checker'ы по строгости гарантии, которую они способны обнаружить,
получится примерно такая шкала:

1. **`patroni-set` / `checker/set`** — сравнение множеств «в начале» и «в конце»,
   без учёта порядка и параллелизма. Ловит только потерю/появление элементов.
2. **`checker/set-full`** — то же самое, но с учётом времени: различает «элемент
   появился с задержкой» (`stale`) и «элемент пропал насовсем» (`lost`), опционально
   требует линеаризуемости появления.
3. **Knossos (`checker/linearizable`)** — полная линеаризуемость истории относительно
   модели одного объекта (регистр, CAS, множество, очередь), с учётом всех
   пересечений интервалов операций.
4. **Elle** — семейство уровней транзакционной изоляции для многообъектных транзакций,
   через поиск циклов в графе зависимостей, на порядки быстрее Knossos на больших
   историях.

`patroni-set` находится на первом, самом слабом уровне этой шкалы — отсюда и все
пробелы, перечисленные в разделе «какие гарантии не проверяются» ниже: отсутствие
проверки порядка (пункт 3 в шкале — задача Knossos) и отсутствие проверки
транзакционной изоляции при конкурентных SQL-операциях (пункт 4 — задача Elle). Ни
Knossos, ни Elle в `patroni-test` не подключены.

## Разбор `patroni-set`

```clojure
(def patroni-set
  "Given a set of :add operations followed by a final :read, verifies that
  every successfully added element is present in the read, and that the read
  contains only elements for which an add was attempted."
  (reify checker/Checker
    (check [this test history opts]
      (let [attempts (->> history
                           (r/filter op/invoke?)
                           (r/filter #(= :add (:f %)))
                           (r/map :value)
                           (into #{}))
            adds (->> history
                      (r/filter op/ok?)
                      (r/filter #(= :add (:f %)))
                      (r/map :value)
                      (into #{}))
            final-read (->> history
                             (r/filter op/ok?)
                             (r/filter #(= :read (:f %)))
                             (r/map :value)
                             (reduce (fn [_ x] x) nil))]
        (if-not final-read
          {:valid? false
           :error  "Set was never read"}
          (let [ok          (set/intersection final-read attempts)
                unexpected  (set/difference final-read attempts)
                lost        (set/difference adds final-read)
                recovered   (set/difference ok adds)]
            {:valid?          (and (empty? lost) (empty? unexpected))
             :ok              (util/integer-interval-set-str ok)
             :lost            (util/integer-interval-set-str lost)
             :unexpected      (util/integer-interval-set-str unexpected)
             :recovered       (util/integer-interval-set-str recovered)
             :ok-frac         (util/fraction (count ok) (count attempts))
             :unexpected-frac (util/fraction (count unexpected) (count attempts))
             :lost-frac       (util/fraction (count lost) (count attempts))
             :recovered-frac  (util/fraction (count recovered) (count attempts))}))))))
```

Модель нагрузки, которую проверяет этот checker, максимально простая: клиент (см.
`pg-client` в patroni.clj) в течение теста выполняет операции `:add` (вставка одного
значения) и `:read` (чтение всего текущего множества), генерируемые функциями `a` и
`r`. Значение для `:add` берётся из глобального атома-счётчика `register`, то есть все
значения заведомо уникальны — это важно, множества здесь работают как append-only
журнал, а не как структура с повторами.

### `attempts` — что вообще пытались вставить

```clojure
(->> history
     (r/filter op/invoke?)
     (r/filter #(= :add (:f %)))
     (r/map :value)
     (into #{}))
```

Берутся **все** `:invoke`-операции с `:f :add`, независимо от того, чем они завершились
(`:ok`, `:fail` или `:info`, или вовсе не завершились). Это множество всех значений, для
которых клиент когда-либо пытался выполнить `INSERT`. `attempts` — верхняя граница:
всё, что могло появиться в базе, лежит внутри `attempts` (при условии уникальности
генерируемых значений).

### `adds` — что точно вставилось

```clojure
(->> history
     (r/filter op/ok?)
     (r/filter #(= :add (:f %)))
     (r/map :value)
     (into #{}))
```

Берутся только те `:add`, которые завершились `:ok` — то есть INSERT точно выполнился и
клиент получил об этом подтверждение. `adds` — нижняя граница гарантированно
записанных элементов: подмножество `attempts` (`adds ⊆ attempts`), в которое **не**
попадают операции с исходом `:info` (таймаут, обрыв соединения, read-only ошибка и
т.п.) — по семантике из документа про Client, `:info` означает «эффект неизвестен», а
не «эффекта нет», поэтому эти значения не могут считаться ни точно вставленными, ни
точно потерянными на этом этапе.

### `final-read` — что реально видно в конце

```clojure
(->> history
     (r/filter op/ok?)
     (r/filter #(= :read (:f %)))
     (r/map :value)
     (reduce (fn [_ x] x) nil))
```

Здесь важная деталь: это **не** обязательно последняя по времени `:read`-операция в
истории, а **последняя из успешных** (`:ok`) `:read`-операций в порядке их следования в
history. `reduce (fn [_ x] x)` последовательно перезаписывает аккумулятор, так что в
итоге остаётся значение самого последнего `:ok`-чтения. Если после него в истории были
ещё чтения, но они завершились `:fail`/`:info` (например, упали из-за обрыва
соединения на упавшей ноде), они игнорируются, и checker «откатывается» к последнему
удачному чтению. Значение уже приходит как Clojure-множество, потому что клиент сам
оборачивает результат SQL-запроса в `(vec) (set)` — то есть **дедупликация читаемых
значений происходит на стороне Client, а не Checker**: если СУБД физически вернула бы
дубликат строки, checker об этом никогда не узнает.

Если `final-read` оказался `nil` (ни одного успешного чтения за весь тест), checker
сразу возвращает `{:valid? false, :error "Set was never read"}`, даже не пытаясь
анализировать `:add`. Это осознанное отличие от встроенного `jepsen.checker/set`,
который в такой ситуации возвращает `{:valid? :unknown, :error "Set was never read"}`
— то есть трактует отсутствие финального чтения как «нельзя ничего сказать», тогда как
`patroni-set` трактует это как жёсткий провал теста.

### `ok`, `lost`, `unexpected`, `recovered`

```clojure
ok          (set/intersection final-read attempts)
unexpected  (set/difference final-read attempts)
lost        (set/difference adds final-read)
recovered   (set/difference ok adds)
```

| Множество | Формула | Смысл |
|---|---|---|
| `ok` | `final-read ∩ attempts` | Значения, которые действительно пытались добавить и которые видны в финальном чтении. Ожидаемый, «здоровый» случай. |
| `lost` | `adds \ final-read` | Значения, которые **точно** были подтверждены (`:ok`), но пропали к финальному чтению — прямое нарушение durability. |
| `unexpected` | `final-read \ attempts` | Значения в финальном чтении, для которых **вообще не было** попытки `:add` в этом прогоне теста — признак порчи/подмены состояния (чужие данные, остатки прошлого запуска, split-brain-дублирование и т.п.). |
| `recovered` | `ok \ adds` | Значения, для которых исход `:add` был неопределённым (`:info`), но они всё же обнаружились в финальном чтении — операция «на самом деле» прошла, просто клиент об этом не узнал вовремя. Это ожидаемая и допустимая ситуация, а не нарушение. |

Итоговый вердикт:

```clojure
:valid? (and (empty? lost) (empty? unexpected))
```

То есть тест валиден тогда и только тогда, когда **нет потерянных** и **нет
посторонних** записей. Наличие `recovered` (неопределённых операций, которые всё же
подтвердились) на `:valid?` не влияет — это ожидаемое поведение при сетевых
разделениях/убийствах процессов и не считается нарушением.

Дополнительно вычисляются доли (`util/fraction`) каждого множества относительно
`attempts` — `:ok-frac`, `:lost-frac`, `:unexpected-frac`, `:recovered-frac` — чисто
информационные метрики для отчёта, на `:valid?` не влияют.

## Какие гарантии проверяются

- **Durability подтверждённых записей.** Если клиент получил `:ok` на `:add`, это
  значение обязано быть видно в финальном состоянии множества. Потеря такой записи
  (`lost`) — прямое нарушение, тест падает. Это основной инвариант, ради которого
  checker существует: смерть процесса, split-brain, потеря лидерства не должны терять
  уже подтверждённые клиенту записи.
- **Отсутствие «чужих»/сфабрикованных данных.** Финальное чтение не должно содержать
  значений, которые вообще не встречались среди `:add`-попыток этого теста
  (`unexpected`). Это ловит порчу состояния — например, если после split-brain и
  восстановления в таблице оказались строки не из этого прогона, либо если
  read-запрос вернул мусор из-за рассинхронизации реплик.
- **Совместимость с неопределённым исходом (`:info`).** Значения с неясным результатом
  `:add`, которые всё же нашлись в финальном чтении (`recovered`), не наказываются —
  checker корректно следует принципу «`:info` не означает `:fail`».

Оба проверяемых свойства (`lost` и `unexpected`) в сумме соответствуют классическому
критерию **at-least-once + no-fabrication** для множества под нагрузкой сбоев:
"всё подтверждённое сохраняется, и ничего не появляется из ниоткуда".

## Какие гарантии не проверяются

- **Линеаризуемость / упорядоченность операций.** Checker вообще не смотрит на времена
  начала/конца операций и не строит частичный порядок — он анализирует только конечные
  множества `attempts`/`adds`/`final-read`, без учёта того, *в каком порядке* значения
  появлялись. Например, если `:add(5)` произошёл после того, как клиент уже увидел
  `:read` без 5, но 5 всё равно оказалась в финальном чтении, checker этого не заметит
  как аномалию (в отличие от `checker/linearizable` или `checker/set-full`, которые
  умеют это отслеживать через `last-present`/`last-absent`). Именно эту проверку и
  выполняет **Knossos** — но он в `patroni-test` не подключён.
- **Транзакционная изоляция при конкурентных операциях.** `pg-client` выполняет `:read`
  как `SELECT ... FOR UPDATE` и `:add` как отдельный `INSERT` — оба вне явных
  многошаговых транзакций с точки зрения checker'а. Даже если бы Patroni/Postgres
  допускал аномалии изоляции при высоком параллелизме (грязное чтение, потерянное
  обновление, аномалии сериализуемости), `patroni-set` не способен их обнаружить — он
  не строит граф зависимостей между операциями и не ищет в нём циклы. Это зона
  ответственности **Elle**, которая тоже не подключена ни в `patroni-test`, ни в
  `postgres-test` (в показанном коде `checker.clj` есть только слой Knossos).
- **Промежуточные чтения игнорируются.** Проверяется только *последнее* успешное
  чтение. Если в середине теста происходили аномальные чтения (например, «мигание»
  элемента — то есть исчезал и появлялся снова), а к концу теста финальное чтение
  случайно оказалось «правильным», checker сочтёт тест валидным, хотя фактически была
  временная потеря консистентности. Для такого сценария нужен более строгий
  `checker/set-full` с параметром `:linearizable?`.
- **Дублирование записей.** Дедупликация происходит на уровне SQL-клиента (`(vec)
  (set)` в `pg-client`), до того как значение попадает в checker. Если бы СУБД реально
  вернула одну и ту же запись дважды, `patroni-set` об этом никогда бы не узнал —
  готовый `checker/unique-ids` или анализ `duplicated` в `checker/set-full` для этого
  специально существуют, но здесь не задействованы.
- **Причинно-следственная связь с конкретным nemesis-событием.** Checker не сопоставляет
  найденные `lost`/`unexpected` записи с конкретными интервалами `:kill`/`:switch` в
  истории — он лишь констатирует факт нарушения на всей истории целиком. Локализация
  «какая именно атака вызвала потерю» — задача человека, читающего итоговый отчёт
  (используя таймстемпы истории вручную), а не самого checker'а.
- **Гарантии для операций `:fail`.** Значения, чьи `:add` завершились явным `:fail`
  (не `:info`), не входят ни в `attempts`… на самом деле входят — `attempts` берёт все
  `:invoke`, независимо от исхода. Но такие значения не входят в `adds`, поэтому их
  отсутствие в финальном чтении не считается потерей — это корректно (раз `:fail`
  означает «эффекта точно нет»). Однако если такое значение **всё же** появилось бы в
  финальном чтении, checker классифицировал бы его не как аномалию, а как `ok`
  (`ok = final-read ∩ attempts`, а `attempts` включает и провалившиеся попытки) — то
  есть checker не отличает «подтверждённо провалившийся, но неожиданно появившийся»
  `:add` от `:info`-операции с тем же исходом. Строго говоря, это небольшой пробел:
  появление в чтении значения из явно `:fail`-операции — тоже аномалия (СУБД
  задним числом «ожила» операция, которая должна была гарантированно не примениться),
  но `patroni-set` её не ловит отдельно.

## Примеры минимальных history

Ниже — иллюстративные (упрощённые) фрагменты history и то, что вычислит `patroni-set`.
Поля `:index`/`:time` опущены для краткости.

**1. Всё хорошо (valid = true)**

```clojure
[{:type :invoke, :process 0, :f :add,  :value 1}
 {:type :ok,     :process 0, :f :add,  :value 1}
 {:type :invoke, :process 0, :f :read, :value nil}
 {:type :ok,     :process 0, :f :read, :value #{1}}]
```
`attempts=#{1}`, `adds=#{1}`, `final-read=#{1}` → `ok=#{1}`, `lost=#{}`,
`unexpected=#{}` → **`:valid? true`**.

**2. Потерянная запись (durability нарушена)**

```clojure
[{:type :invoke, :process 0, :f :add,  :value 1}
 {:type :ok,     :process 0, :f :add,  :value 1}
 {:type :invoke, :process 0, :f :read, :value nil}
 {:type :ok,     :process 0, :f :read, :value #{}}]
```
`adds=#{1}`, `final-read=#{}` → `lost=#{1}` → **`:valid? false`** (запись подтверждена,
но исчезла — типичный симптом при `:kill` без успешной репликации).

**3. Посторонняя запись (порча состояния)**

```clojure
[{:type :invoke, :process 0, :f :read, :value nil}
 {:type :ok,     :process 0, :f :read, :value #{42}}]
```
`attempts=#{}`, `final-read=#{42}` → `unexpected=#{42}` → **`:valid? false`** (в базе
значение, которое в этом тесте никто не добавлял — например, остаток предыдущего
прогона, не подчищенный при `--existing-postgres`).

**4. Recovered — неопределённый исход, но данные на месте (valid = true)**

```clojure
[{:type :invoke, :process 0, :f :add,  :value 1}
 {:type :info,   :process 0, :f :add,  :value 1, :error "timeout"}
 {:type :invoke, :process 0, :f :read, :value nil}
 {:type :ok,     :process 0, :f :read, :value #{1}}]
```
`attempts=#{1}` (invoke учитывается независимо от исхода), `adds=#{}` (только `:ok`
считается подтверждённым), `final-read=#{1}` → `ok=#{1}`, `recovered = ok \ adds = #{1}`
→ **`:valid? true`** (потери и постороннего значения нет; неопределённость исхода не
наказывается).

**5. Множество ни разу не прочитано**

```clojure
[{:type :invoke, :process 0, :f :add, :value 1}
 {:type :ok,     :process 0, :f :add, :value 1}]
```
`final-read = nil` → сразу **`{:valid? false, :error "Set was never read"}"`**, без
дальнейшего анализа `attempts`/`adds` (жёсткое требование, отличающее `patroni-set` от
встроенного `checker/set`, который в этом случае вернул бы `:unknown`).
