# Jepsen-тест плановых переключений PostgreSQL HA (Patroni) 

Тест проверяет, что HA-система для PostgreSQL выдерживает плановую смену лидера (`switchover`) в том числе во время network partitions. Сейчас тест написан под Patroni.

Что делает тест:

1. определяет начального лидера.
2. обходит все нужные пары «лидер → кандидат» (каждую ровно один раз), на каждом переходе выдаёт `switchover` и проверяет, что кластер пришёл к ожидаемой топологии и удерживает её.
3. параллельно раз в секунду снимает состояние всех узлов, а nemesis циклически создаёт и снимает network partitions.
4. после каждого network partition проверяет, что кластер восстановился.
5. по записанной истории выносит вердикт и печатает сводку по таймингам.

SQL-нагрузки и проверки сохранности записей здесь нет: проверяются переключение, наблюдаемая топология и время сходимости.

## Запуск

Нужен Docker. Из каталога `jepsen/`:

```bash
./run-test                                  # собрать и поднять стенд с конфигурацией по умолчанию (default.yaml)
./run-test --profile profiles/other.yaml    # сборка и запуск с указанием своей конфигурации
```

`run-test`:

1. поднимает docker стенд `docker compose up -d --build` и запускает тест в контейнере `test`.
2. после теста копирует результаты на хост в `jepsen/store/patroni/<время>/` (`latest` — ссылка на последний прогон): `history.edn`, `results.edn`, `jepsen.log`, `timeline.html`.
3. останавливает стенд (`docker compose down -v`). Чтобы оставить его поднятым для отладки, задайте `JEPSEN_KEEP_STAND=1`.
4. завершается.


Стенд (см. `docker-compose.yml`): три узла Patroni (`patroni1..3`), три узла etcd (`etcd1..3`) и контейнер `test` с Jepsen. Учётные данные REST API Patroni берутся из переменных окружения`PATRONI_RESTAPI_USERNAME` и `PATRONI_RESTAPI_PASSWORD`.

В консоль идут статус-строки по событиям (`switch #2 node-a -> node-c, attempt 1: ok`, `partition applied: …`, `partition healed`), блок `HA summary` и стандартный итог Jepsen. Вся история прогона хранится в `history.edn`.

## Структура репозитория

```
Dockerfile, docker-compose.yml      стенд: образы etcd, Patroni и контейнер с Jepsen
runit/                              запуск etcd и Patroni внутри контейнеров
jepsen/
  project.clj                       файл зависимостей
  run-test                          запуск стенда и теста
  profiles/default.yaml             файл конфигурации
  src/jepsen/patroni.clj            сборка теста, клиент, генератор, -main
  src/jepsen/ha/patroni_system.clj  доступ к кластеру Patroni (наблюдение, switchover)
  src/jepsen/ha/plan.clj            план переключений (эйлеров цикл) и его генератор
  src/jepsen/ha/fault.clj           nemesis'ы
  src/jepsen/ha/checker.clj         checker 
  src/jepsen/ha/profile.clj         обработка файла конфигурации
```

## Что взято из Jepsen


| Компонент | Что он даёт | Как используется в проекте |
|---|---|---|
| Карта теста | `jepsen.tests/noop-test` | Базовая конфигурация `patroni-test`. Jepsen не устанавливает кластер: `db`, `os`, сеть и удалённое управление остаются стандартными компонентами `noop-test`; стенд запускается отдельно через Docker Compose. |
| Командная строка | `jepsen.cli/single-test-cmd`, `jepsen.cli/run!` | Точка входа `-main` разбирает аргументы и запускает тест Jepsen. |
| Клиент | `jepsen.client/Client`, `Reusable` | Проект реализует клиент с операциями `:observe`, `:leader` и `:switch`. |
| Жизненный цикл | `jepsen.core/run!`, `jepsen.store` | Jepsen запускает клиентские и nemesis-операции, передаёт историю checker-ам и сохраняет историю и результаты. Скрипт `run-test` дополнительно копирует файлы прогона из контейнера на хост. |
| Потоки и история | `jepsen.generator.interpreter` | Jepsen выдаёт операции двум клиентским потокам и отдельному потоку nemesis, записывая вызовы и завершения в историю. В `patroni.clj` поток `:observer` только опрашивает кластер, а `:switcher` определяет начального лидера и выполняет переключения. Немезис управляет сетевыми разделениями. Благодаря этому опросы продолжаются во время переключений, а одновременно выполняется не более одного `:switch`. |
| Генераторы | `jepsen.generator` | Генераторы задают расписание фаз и операций: начальное определение лидера, переключения, опросы примерно раз в секунду и циклы сетевых разделений. Самописный`MainPhase` координирует план(эйлеров цекл) с этими операциями. |
| Сетевой немезис | `jepsen.nemesis/partitioner` и функции построения grudge | Стандартный partitioner применяет и снимает правила `iptables`. В `fault.clj` выбирается один из шаблонов разделения: `random-node`, `random-halves` или `majorities-ring`. |
| Стандартные checker-ы | `jepsen.checker/compose`, `stats`, `unhandled-exceptions` | Включены в общий checker для статистики операций и обнаружения необработанных исключений; проверку HA выполняет собственный самописный checker. |
| Управление узлами и время | `jepsen.control`, `jepsen.util` | `jepsen.control` запускает `patronictl` по SSH; функции `jepsen.util` используются для измерения времени операций. |

Сторонние библиотеки: `http-kit` (REST-запросы), `clj-yaml` (профиль), `data.json` (разбор ответов Patroni).

## Самописное


| Часть проекта | Файл | Назначение |
|---|---|---|
| Работа с Patroni | `ha/patroni_system.clj` | Получает снимки через REST API Patroni, проверяет готовность кандидата по `/sync` и `/quorum`, запускает `patronictl switchover` по SSH и сопоставляет идентификаторы узлов с именами членов patroni кластера. |
| Загрузка профиля | `ha/profile.clj` | Читает и проверяет YAML-профиль:  Настройки теста и ожидаемая топология кластера |
| План переключений | `ha/plan.clj` | Строит эйлеров цикл по заданным направленным переходам, чтобы обойти все переходы из каждого узла.  |
| Тест Jepsen | `src/jepsen/patroni.clj` | Здесь собраны клиент, генератор операций и конфигурация теста. В начале клиент определяет лидера: доступные узлы должны сообщить об одном и том же лидере в нескольких опросах подряд. Затем генератор выполняет переходы из конфигурационного файла, пока отдельный поток опрашивает узлы, а немезис запускает сетевые разделения. Для каждого перехода клиент проверяет готовность кандидата, вызывает `patronictl switchover` и ждёт, пока все узлы сообщат ожидаемую топологию заданное число опросов подряд. |
| Генератор сетевых сбоев | `src/jepsen/ha/fault.clj` | Для каждого цикла выбирает один из трёх шаблонов разделения узлов, ждёт заданный случайный интервал, включает разделение, выдерживает его заданное время и восстанавливает сеть. События включения и восстановления записываются в журнал. Сетевые правила применяет partitioner Jepsen. |
| Проверка истории | `src/jepsen/ha/checker.clj` | Для каждого переключения checker требует завершение `:ok` и не менее `stable-samples` последовательных снимков, в которых все узлы доступны и сообщают ожидаемые роли и одного лидера-кандидата. В снимках вне сетевого сбоя после этого переключения не должно быть другой топологии; если история заканчивается раньше, достаточно, чтобы её последние снимки образовали нужную последовательность. После снятия сетевого разделения checker требует такую же последовательность снимков с любой допустимой топологией в пределах `convergence.timeout-seconds`. По этим проверкам он выставляет итоговый `:valid?` и рассчитывает сводку по времени. |
| Сборка и запуск стенда | `run-test`, `Dockerfile`, `docker-compose.yml`, `runit/` | `docker-compose.yml` описывает контейнер теста, три узла etcd и три узла Patroni. `Dockerfile` собирает образы, а скрипты `runit/etcd/run` и `runit/patroni/run` запускают службы в контейнерах. `run-test` поднимает стенд, запускает тест и копирует результаты на хост; затем останавливает стенд, кроме случаев, когда задано `JEPSEN_KEEP_STAND=1`. |

## Конфигурация теста

Параметры ниже сверены с `jepsen/profiles/default.yaml`. Три необязательные настройки, которых в этом файле нет, отмечены отдельно; другой профиль задаётся опцией `--profile` или переменной окружения `JEPSEN_HA_PROFILE`.

| Параметр | Что задаёт | В `default.yaml` или если настройка опущена |
|---|---|---|
| `nodes` | Узлы кластера: у каждого задаются уникальные `id` и `ssh-host`; нужно не меньше двух узлов. | Обязателен |
| `patroni.nodes.<id>.rest-api` | Адрес REST API Patroni для узла с указанным `id`. | Обязателен для каждого узла |
| `switchover.max-attempts` | Максимальное число попыток для одного перехода. | В YAML задано `3`; если ключ опустить, будет `3` |
| `switchover.pause-seconds` | Пауза между успешными переключениями. | В YAML задано `60` секунд; если ключ опустить, будет `60` секунд |
| `convergence.poll-interval-seconds` | Интервал между опросами состояния узлов. | В YAML задана `1` секунда; если ключ опустить, будет `1` секунда |
| `convergence.stable-samples` | Число одинаковых корректных снимков подряд, необходимое для признания состояния устойчивым. | В YAML задано `3`; если ключ опустить, будет `3` |
| `convergence.timeout-seconds` | Предельное время одного ожидания: определить общего лидера в начале теста, дождаться готовности кандидата или ожидаемой топологии после переключения. При проверке восстановления после сетевого разделения этот срок отсчитывается от восстановления сети. | В YAML задано `60` секунд; если ключ опустить, будет `60` секунд |
| `nemesis.cycles` | Число циклов сетевых разделений. | `6` в `default.yaml`; без секции `nemesis` сбои не запускаются |
| `nemesis.duration-seconds` | Как долго удерживать сетевое разделение. | `60` секунд в `default.yaml` |
| `nemesis.interval-seconds` | Базовая пауза до разделения; фактическая пауза случайна и составляет от 1 до 2 интервалов. | `30` секунд в `default.yaml` |
| `connectivity` | Необязательный список пар узлов, между которыми можно планировать переключения. Каждая пара действует в обе стороны. | Не задано: разрешены все пары разных узлов |
| `transitions` | Необязательный список направленных переходов `[лидер, кандидат]`. | Не задано: используются все упорядоченные пары, разрешённые настройкой `connectivity` |

Например, эта настройка разрешает переключения между `node-a` и `node-b`, а также между `node-b` и `node-c`:

```yaml
connectivity:
  - [node-a, node-b]
  - [node-b, node-c]
```

`transitions` задаёт конкретные направленные переходы `[текущий лидер, кандидат]`. Например, цикл ниже сначала переключает лидерство с `node-a` на `node-b`, затем на `node-c` и обратно на `node-a`:

```yaml
transitions:
  - [node-a, node-b]
  - [node-b, node-c]
  - [node-c, node-a]
```

`patroni.command-timeout-seconds` — ещё одна необязательная настройка, которой нет в `default.yaml`. Она ограничивает время выполнения `patronictl switchover`; если её не задать, используется 10 секунд. Чтобы переопределить таймаут, добавьте ключ на верхнем уровне секции `patroni`, рядом с `nodes`.

```yaml
patroni:
  command-timeout-seconds: 20
  nodes:
    # адреса REST API узлов
```
Ожидаемая топология выводится из списка узлов: при лидере `X` остальные — реплики, и все узлы входят в кластер. Пользовательский список `transitions` должен образовывать эйлеров цикл: каждый узел в нём имеет одинаковое число входящих и исходящих переходов, а все переходы входят в один связный цикл.

## Как читать результат

В `HA summary` по каждому переключению: `command` — длительность самой команды `switchover`; `target` — время от начала команды до первого снимка с целевой топологией; `stable` — время до устойчивой целевой топологии (`stable-samples` снимков подряд). По каждому partition: `recovery` — время от снятия network partition до устойчивой допустимой топологии. Значение `-` - события не произошло. Результат валиден (`:valid? true`), если все запланированные переходы завершились `:ok` и устоялись, а после всех partitions кластер восстановился.

## Контракт истории

Checker и план читают только историю Jepsen:

- `:observe` → значение `{:observations [{:node :reachable? :postgres-role :ha-role :leader :members …} …]}`;
- `:leader` → id начального лидера;
- `:switch` — вызов `{:from :candidate :attempt :index}`, завершение дополнительно содержит `:result`/`:error`, `:command-start`, `:command-ms`;
- процесс `:nemesis`: завершение `:start` со значением `[:isolated grudge]` — partition применён, завершение `:stop` со значением `:network-healed` — сеть исцелена.


## Ограничения

- Проверена конфигурация из трёх узлов Patroni/PostgreSQL и etcd в Docker. Другое число узлов задаётся профилем, но докер образы для него нужно описать самостоятельно путём редоктирования докер файлов.
- Воздействия на процессы (kill, pause) нет, только network partitions.
